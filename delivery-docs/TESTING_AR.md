# الاختبارات وحدود النسخة

## اختبارات المصدر

بعد تثبيت dependencies ومن جذر المشروع:

```sh
node --check public/mirsad.js
node node_modules/typescript/bin/tsc --noEmit
node tests/contracts.mjs
node tests/database.mjs
node tests/triage.mjs
node tests/priority-ui.mjs
node tests/ticket-impact.mjs
node tests/notifications-ui.mjs
pnpm build
```

- `database.mjs`: يشغّل migrations كلها في PostgreSQL مضمّن عبر PGlite، مع أدوار وحسابات اصطناعية. يشمل RLS والترقيم والتسليم وإشعارات المستلمين والقراءة الخاصة وبيانات التواصل. لا يضيف هذه البيانات إلى Supabase الفعلي.
- `contracts.mjs`: حدود الحقول ورفض أولوية أو مالك يختاره المستخدم والتحقق من التواصل.
- `triage.mjs`: محاكاة Auth وGroq لاختبار schema والتعامل مع الفشل والحصص وإعادة المحاولة وحفظ النتيجة. ظهور أخطاء مصطنعة في الطرفية أثناء هذا الاختبار متوقع إذا انتهى بسطر PASS.
- `priority-ui.mjs`: ظهور المراجعة حسب الدور وإخراج النصوص بأمان.
- `ticket-impact.mjs`: خمسة أسئلة و768 تركيبة، وأطوال الوصف، وفصل الهاتف عن طلب AI، وتحويل الأرقام العربية في الهاتف.
- `notifications-ui.mjs`: العداد وحالة القراءة وعدم تكرار toast وعزل الحسابات ومعالجة عنوان البلاغ كنص.

الاختبارات لا تستخدم مفتاح Groq حقيقيًا ولا تستهلك طلبات توليد. ملف `tests/dialect-cases.json` يحتوي أمثلة لتقييم النموذج الحقيقي، لكن ليس دليلًا على دقته دون تشغيل تقييم مستقل ومراجعة بشرية.

## تجربة قبول واقعية

استخدمي حساب مستخدم وحسابي فنيين معتمدين في ملفات متصفح أو أجهزة منفصلة، حتى لا تختلط الجلسات:

1. أنشئي بلاغًا واضحًا مع بيانات الموقع والجوال والأسئلة الخمسة.
2. تحققي من الرقم وسبب الأولوية وظهور الموقع والتواصل.
3. افتحي حساب فني آخر؛ يظهر إشعار بعد دورة التحقق التالية أو تحديث الصفحة. البلاغات القديمة قبل إضافة ميزة الإشعارات لا تُنشئ إشعارات تاريخية تلقائيًا.
4. افتحي الإشعار؛ ينخفض عداد الحساب نفسه. لا تتغير قراءة الفني الثاني.
5. استلمي معالجة البلاغ، ثم افتحي «تسليم البلاغ لفني آخر» وأرسلي ملخصًا للفني الثاني.
6. قبل القبول تأكدي أن المسؤول هو الأول. من حساب الثاني اقبلي بعد المراجعة؛ تتغير المسؤولية.
7. جرّبي الرفض مع سبب، والطلب المكرر، وإعادة التسليم من المالك الجديد.
8. من حساب موظف مختلف تأكدي من عدم الوصول إلى البلاغ أو بيانات التواصل أو إشعارات الفنيين.
9. جرّبي وصفًا غامضًا واختبار فشل الخدمة في بيئة مخصصة؛ يجب حفظ البلاغ وإحالته للمراجعة دون أولوية تخمينية.
10. اختبري تأكيد البريد واستعادته والعودة إلى أصل مرصاد الصحيح.

لا تمسحي بيانات فعلية أو تغيّري أسرار الإنتاج بغرض التجربة. استخدمي مشروعًا منفصلًا للاختبارات التي تتعمد تعطيل الخدمة.

## حدود مهمة للمطور

- التطبيق لمساحة دعم واحدة. لا يوجد عزل مؤسسات متعددة عبر tenant membership.
- قائمة البلاغات محدودة بآخر 200 بلاغ، وقراءة مجموعات السجلات الفرعية محدودة؛ يلزم pagination عند زيادة الحجم. البحث الحالي ضمن البيانات المحملة.
- قائمة الإشعارات تعرض آخر 100، والعداد يحسب كل غير المقروء. فتح إشعار قديم خارج نطاق البلاغات المحملة يحتاج توسيع الجلب/التصفح في تطوير لاحق.
- الإشعارات داخل التطبيق فقط، وتتحدث كل 15 ثانية في التبويب الظاهر؛ لا يوجد Web Push أو بريد أو SMS عند إغلاق المتصفح.
- لا توجد مرفقات أو SSO مؤسسي أو SLA تعاقدي أو ضمان دقة AI لكل لهجة.
- الشاشة العامة وفحص الجاهزية لا يثبتان أن نموذج AI الحقيقي صنّف بلاغًا بنجاح.
- في المخطط الحالي حماية البيانات تعتمد على الصلاحيات ودوال RPC المحددة. لا تمنحي أذونات تعديل عامة للجداول لتجاوز خطأ دون فهم أثره.
- نشر مصدر معدّل يحتاج اختبارًا وبناءً ونشرًا جديدًا. حفظ الملف في VS Code وحده لا يغير الموقع المنشور.
