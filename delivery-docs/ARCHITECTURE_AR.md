# تفاصيل بنية مِرصاد

## التقنيات

- TypeScript وJavaScript للمنطق، وReact لتهيئة العرض.
- Vinext/Vite مع Cloudflare Workers للخادم. المشروع يستخدم بنية مسارات شبيهة بـNext.js، وليس تطبيق Next.js قياسيًا يُنقل إلى أي استضافة دون مراجعة.
- HTML داخل `app/shell.ts`، وعرض صفحات ديناميكي داخل `public/mirsad.js`.
- CSS وخطوط مضمّنة وشعار SVG. البترولي افتراضي، مع ملفات الاحتفاظ بالمقارنة البنفسجية.
- Supabase Auth للحسابات وPostgreSQL للبيانات وRLS للصلاحيات.
- Supabase Edge Function لتنفيذ استدعاء Groq من الخادم.
- Zod للتحقق من مدخلات API ونتائج النموذج.

## تدفق البلاغ

1. يملأ الموظف العنوان والتصنيف والموقع التفصيلي والجوال والوصف وخمسة أسئلة.
2. تُضم إجابات الأسئلة إلى الوصف بنص واضح. بيانات الموقع والجوال تُرسل في كائن `contact` منفصل؛ لا تدخل في طلب AI المعدّ من حقول النموذج.
3. الواجهة تنشئ UUID خاصًا بعملية الإرسال لمنع إنشاء بلاغات مكررة بسبب إعادة الطلب.
4. الخادم يتحقق من جلسة Supabase الفعلية ومن المصدر Origin وصحة JSON وحدود الحقول.
5. الخادم يستدعي `create_ticket_with_contact` للطلبات الجديدة مع بيانات التواصل، أو المسار القديم المتوافق `create_ticket` عندما لا تكون موجودة.
6. معاملة قاعدة البيانات تتحقق من المستخدم وتخصص الرقم المركزي وتضيف البلاغ ومهمة أولية وحدث إنشاء. الدالة الموسّعة تحفظ بيانات التواصل في المعاملة نفسها.
7. Trigger الإنشاء يضيف إشعارات للفنيين المعتمدين والمسؤولين باستثناء منشئ البلاغ.
8. الخادم يرسل رقم البلاغ وJWT إلى Edge Function؛ وظيفة AI تعيد التحقق من المستخدم وتحجز مهمة تحليل مرتبطة بالبلاغ.
9. يُرسل إلى Groq العنوان والوصف والتصنيف، ومعها ملاحظات المتابعة المحدودة في إعادة التحليل. إذا كتب المستخدم بنفسه معلومات شخصية في الوصف أو الملاحظات فهي جزء من النص؛ الفصل يخص حقول التواصل المخصصة.
10. يُفحص JSON الناتج ويُحفظ عبر دالة خاصة بالخدمة. إذا فشل المزوّد أو كان الوصف غامضًا، يبقى البلاغ محفوظًا ويحال إلى المراجعة دون أولوية مختلقة.

## الأولوية

تعليمات النموذج الفعلية في `triage.ts` هي المرجع. يقيّم نطاق التأثير، وتعطّل العمل، والمخاطر، ووجود بديل. وقت البداية سياق إضافي؛ طول المدة وحده ليس قاعدة آلية تجعل كل بلاغ عاليًا.

- عالية: خطر أمني/فقدان بيانات موثوق أو توقف خدمة مشتركة أساسية أو تعطّل واسع يوقف العمل دون بديل عملي مذكور.
- متوسطة: تعطّل تشغيلي واضح ومحدود، مثل تعطل مستخدم واحد.
- منخفضة: طلب روتيني لا يوقف العمل.
- بحاجة لمراجعة: غموض أو تضارب أو نقص أدلة، أو عدم توفر خدمة AI. لا تكون قيمة الأولوية مخمّنة.

«عاجل» أو الانفعال وحدهما لا يرفعان الأولوية. تعليمات داخل نص البلاغ لا تمنح المستخدم صلاحية اختيارها. وحدهم الفنيون المعتمدون/المسؤول يستطيعون ضبط أولوية الحالات المحالة للمراجعة، مع سبب مسجل. حسم المراجعة يلغي المهمة القديمة كي لا تستبدلها استجابة AI متأخرة.

## الحسابات والصلاحيات

| الدور | ما يمكنه فعله |
|---|---|
| مستخدم | إنشاء بلاغاته وقراءتها ومتابعتها وإضافة توضيحات ضمن العمليات المسموحة |
| طالب اعتماد فني | حساب مستخدم إلى أن يُعتمد؛ لا يكتسب صلاحيات الفني من اختياره في التسجيل |
| فني معتمد | قراءة مساحة الدعم، استلام البلاغات، تحديث خطوات البلاغات التي يملكها، تسليمها، ومراجعة أولوية الحالات المسموح بها |
| مسؤول | صلاحيات الدعم مع اعتماد/رفض طلبات الفنيين |

تعديل `user_metadata` لا يمنح صلاحية إدارية. الصلاحيات تؤخذ من ملفات الحساب في قاعدة البيانات وتُفحص داخل الدوال والسياسات. جمهور الموقع العام يسمح بفتح صفحة الدخول دون حساب ChatGPT، لكنه لا يجعل بيانات البلاغات عامة.

## التسليم

- الموظف ينشئ البلاغ؛ الفني المعتمد يستلمه عبر إجراء `claim`.
- المالك الحالي وحده يرسل طلب التسليم، مع الفني المقصود والسبب والملخص والملاحظات.
- أثناء الانتظار يبقى المالك الأول مسؤولًا. لا يسمح النظام بطلبين معلّقين لنفس البلاغ.
- المستلم المقصود وحده يقبل أو يرفض. القبول يحتاج إقرار مراجعة، والرفض يحتاج سببًا.
- قبول الطلب يحدّث المالك ويكتب الحدث في المعاملة نفسها. الرفض يبقي المالك الأول.
- يستطيع المالك الجديد إعادة التسليم لاحقًا. التوثيق ينتقل مع البلاغ.

## الإشعارات

- جدول `notifications` يحفظ المستلم والبلاغ ونوع الإشعار وعنوانه ووقت الإنشاء والقراءة.
- `notify_ticket_created` يرسل إشعارًا للحسابات الفنية المعتمدة/المسؤولين الموجودة وقت الإنشاء.
- `notify_handover_created` ينشئ إشعارًا للمستلم المحدد فقط.
- لا يمنح اعتماد فني جديد لاحقًا إشعارات تاريخية سابقة تلقائيًا.
- `notification_feed` يعيد آخر 100 إشعار للحساب وعدّادًا كاملًا لغير المقروء. `read_notifications` يحدّث القراءة فقط للحساب نفسه.
- إشعارات داخل التطبيق مع polling كل 15 ثانية في التبويب الظاهر. لا يوجد SMS أو بريد أو Web Push خارج المتصفح.
- لا يرسل التطبيق تنبيه toast عن كل القديم عند الدخول؛ يظهر العداد والقائمة. الجديد أثناء الجلسة يظهر كتنبيه داخلي.

## جداول قاعدة البيانات

| الجدول | الغرض |
|---|---|
| `profiles` | الدور والاسم وحالة اعتماد الفني والبيانات الوظيفية |
| `tickets` | البلاغ ومالكه ووصفه وأولوية التحليل وبيانات التواصل |
| `ticket_counter` | ترقيم البلاغات داخل معاملة بقفل مركزي |
| `ticket_tasks` | خطوات العمل وحالتها |
| `ticket_events` | السجل والملاحظات والقرارات |
| `handovers` | طلبات التسليم والقبول والرفض |
| `handover_drafts` | مسودات التسليم الخاصة بالمرسل |
| `request_limits` | حدود الاستدعاءات |
| `notifications` | الإشعارات وحالة القراءة لكل حساب |

## واجهات API

| الطريقة | المسار | الغرض |
|---|---|---|
| GET | `/api/config` | قيم الاتصال العامة وحالة الإعداد |
| GET | `/api/state` | بيانات مساحة العمل المسموح بها للحساب |
| GET | `/api/notifications` | موجز إشعارات الحساب |
| POST | `/api/notifications/read` | قراءة إشعار أو تحديد الكل كمقروء |
| POST | `/api/tickets` | إنشاء بلاغ |
| POST | `/api/tickets/:id/action` | إجراء مسموح مثل الاستلام أو التسليم أو إضافة خطوة |
| POST | `/api/tickets/:id/classify` | إعادة محاولة التصنيف ضمن الصلاحيات والحدود |
| POST | `/api/tickets/:id/priority` | مراجعة الأولوية من فني معتمد |
| POST | `/api/technicians/review` | اعتماد/رفض طالب فني من المسؤول |

كل المسارات عدا الإعداد العام تحتاج JWT صالحًا. طلبات POST تحتاج Origin مطابقًا. لا توجد نقطة API ترفع شخصًا إلى مسؤول من الواجهة.
